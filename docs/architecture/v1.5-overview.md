# V1.5 Architecture Overview

## Purpose

V1.5 extends the released V1 deterministic automation lifecycle with one real Cisco IOS XE model-driven path. It preserves branch-01 as the V1 regression environment and evolves access, composition, write-boundary safety, and execution evidence additively.

V1.5 is an engineering-capability release, not a checklist of automation technologies.

## Product Scope

The required production scope is:

```text
existing Cisco IOS/Scrapli CLI path
        +
one Cisco IOS XE NETCONF read/write path
        +
backward-compatible access and composition evolution
        +
stronger immediate pre-write safety
        +
typed non-CLI execution and evidence when required by the first NETCONF write
```

NETCONF is the sole required production model-driven write protocol for `v1.5.0`. RESTCONF remains useful future engineering and practical work, but production RESTCONF write parity is not a release criterion unless a later ADR identifies a distinct engineering requirement.

Ansible, Netmiko, Jinja2, pyATS, telemetry, Day-0/ZTP, Guest Shell, EEM, and related technologies remain valuable in-repository learning and portfolio work. They do not gate the production package release.

## V1 Compatibility Contract

V1.5 must preserve:

- `intent/branches/branch-01.yaml`;
- compatibility with the current `inventory/lab.yaml` form;
- existing `nap validate`, `nap plan`, and `nap deploy` behavior;
- Cisco IOS/Scrapli CLI collection and execution;
- existing targeted-remediation behavior;
- V1 fail-closed, approval, identity, trust, and post-validation guarantees;
- `BranchDeploymentReport` schema version `1` compatibility; and
- branch-01 as the V1 regression and reference environment.

Internal implementation may evolve. Migration must remain additive and backward-compatible unless a later explicit decision changes this contract.

## Selected Engineering Scenario

Branch-01 remains unchanged.

The intended V1.5 model-driven target is a Cisco Catalyst 8000V running IOS XE 17.15.01a in CML 2.10, subject to local environment feasibility verification before implementation. The preferred direction is a second representative branch using the existing branch shape initially. Its switch and supporting topology should remain only as large as the selected engineering scenario requires.

The IOS XE router is the model-driven target. The preferred management direction is a stable routed management loopback reachable through the representative enterprise/core path rather than another dedicated per-device lab OOB interface.

The following remain feasibility decisions and are not established facts:

- exact addressing;
- interface and platform-profile mappings;
- CML nodes, links, and bootstrap sequence;
- reachability and route prerequisites; and
- the exact IOS XE YANG model and path.

V1.5 does not predefine management VRFs, bastions, controllers, break-glass automation, fallback behavior, or a generic management-path taxonomy.

## First Model-Driven Slice

The first NETCONF read capability is interface state. Trusted capability and model inspection against the actual CML image must select the exact YANG model and path before implementation. No model is considered verified by this document.

The first controlled NETCONF remediation should be a description-only change on a non-management, non-routing-critical interface. Full NETCONF parity with CLI routes, OSPF, VLAN, and switchport collection is not required before architecture acceptance.

The existing CLI collection and validation path may remain the complete post-change observation mechanism for the first NETCONF write. This permits the new write path to be verified through an already accepted independent collection implementation.

## Management and Write-Boundary Safety

V1's safety principles remain mandatory. Branch-wide preflight and all operator approvals still occur before the first write. Immediately before each device write, the eventual V1.5 implementation must:

1. re-establish trusted and authenticated target access;
2. re-verify target identity;
3. rebuild the applicable management-safety expectation from current policy and environment;
4. collect fresh state required for that safety decision;
5. validate the fresh safety prerequisites;
6. recompute or verify the still-required remediation;
7. prove equivalence with the exact approved immutable change;
8. fail closed if the remediation differs, disappears, becomes unsupported, or relevant unsupported drift appears;
9. execute the exact approved artifact; and
10. collect fresh complete post-change state and run full desired-state validation.

This sequence reduces the stale-evidence window but does not claim to eliminate time-of-check/time-of-use risk completely. Later implementation work must state the remaining timing and failure semantics honestly.

## Composition Direction

Validate, plan, and deploy should share one explicit application composition root or factory. It selects known implementations using policy and inventory data while preserving separate responsibilities for:

- state collection/provider behavior;
- change rendering;
- execution;
- capability discovery; and
- management-safety evidence.

V1.5 does not require a dynamic or generic plugin-discovery framework.

Declared and allowed capabilities are policy. Live-discovered capabilities are observations. Discovery must not silently authorize an access mechanism or operation that policy did not permit. Unsupported platform, access-method, or operation combinations fail closed before approval or write.

The concrete internal access model and factory interfaces remain implementation decisions. They must be driven by the first real IOS XE adapter and must preserve the V1 inventory form.

## Execution and Evidence Direction

Read-only NETCONF should land before the final model-driven write artifact is designed. The working V1 CLI execution interface must not be replaced speculatively.

The first real NETCONF write should drive the smallest immutable typed artifact needed for non-CLI execution. The human approval preview and the machine payload executed must derive from the same artifact so approval cannot drift from execution.

Schema version `1` remains the released CLI evidence contract and must not change meaning in place. Schema version `2` should be introduced only when a stable model-driven execution must be represented durably. Raw credentials, trust data, connection objects, and unbounded protocol payloads remain excluded from evidence.

## pyATS Position

pyATS may provide independent acceptance evidence for a small number of selected network outcomes. It does not replace NAP validation and is not part of `deployment_service` by default. It may be used as a final acceptance cross-check without becoming a mandatory production runtime dependency.

## Single-Repository Boundary

Production runtime, maintained integrations, topology assets, and practical learning work remain in this canonical repository by default. Same repository does not mean the same Python package, dependency set, CI gate, secret boundary, or support level.

Future directory structure will be introduced only with the first concrete asset. Production code must not import learning labs, and lab credentials, trust state, generated captures, and device outputs must not enter version control. A separate repository requires an actual ownership, security, deployment, access-control, lifecycle, licensing, or release-cadence boundary.

## Production Completion Contract

V1.5 production acceptance requires measurable evidence that:

1. the released branch-01 path remains compatible;
2. one reproducible IOS XE model-driven scenario exists;
3. access and composition distinguish platform, endpoint, and selected access method without protocol policy leaking into domain logic;
4. CLI and NETCONF normalize interface state meaningfully;
5. validate, plan, and deploy share the same explicit composition boundary;
6. immediate pre-write safety uses fresh evidence and stale approved plans fail closed;
7. one harmless NETCONF remediation passes the existing controlled lifecycle;
8. non-CLI execution evidence is explicitly versioned without breaking schema version `1`;
9. new adapter security and failure paths are tested;
10. final CML acceptance proves both branch-01 regression and the selected IOS XE scenario; and
11. documentation and ADRs accurately state the architecture and limitations.

Learning exercises are not production-package completion criteria.

## Explicit Non-Goals for This Architecture Baseline

This documentation does not implement or settle:

- inventory migration details;
- the exact management-safety model;
- the executor artifact type;
- the exact NETCONF YANG model or XML payload;
- schema-version `2` fields;
- RESTCONF production writes;
- arbitrary topology intent;
- automatic protocol or endpoint fallback;
- a plugin framework;
- rollback, retry, or multi-device transaction semantics; or
- the final in-repository lab directory tree.

Those decisions require concrete implementation evidence and, where durable, later ADRs.
